## 5. P0 findings discovered in current source

### P0-A — Persistence endpoint trusts client-authored result

`api/verify/persist.ts` accepts POST requests and forwards `req.body` to `handlePersistenceServerRequest()`. The handler does not authenticate or authorize the caller and does not recompute the deterministic result server-side.

The handler's integrity check only requires non-empty hashes and a finite numeric `overallSimilarity`, then derives the receipt ID from those supplied values. It subsequently inserts with a privileged server client. This is not proof that the submitted score/evidence was produced by the authoritative engine.

### P0-B — Privileged key fallback is unsafe

`persistenceServerHandler.ts` selects `SUPABASE_SERVICE_ROLE_KEY || VITE_SUPABASE_ANON_KEY`. A missing service-role secret silently changes the execution identity instead of failing closed. The server endpoint must never imply a trusted write succeeded under an anonymous key.

### P0-C — Public receipt proves ID/hash correlation, not evidence recomputation

`publicVerificationService.resolveVerification()` checks receipt format, presence of hashes/envelope and the relationship between document hash, evidence hash and derived ID. It does not independently recompute the deterministic evidence from a canonical input. This is a narrower integrity guarantee than an independently certified engine result.

### P0-D — Browser DOCX test is not portable

`e2e/g1-docx-browser-acceptance.spec.ts` points to `C:/Users/faith/Downloads/DIGITAL THERMOMETER real.docx`. The repository already contains DOCX fixtures. The browser acceptance test should use a committed, hash-pinned fixture with a repository-relative path.

### P0-E — No automated GitHub CI gate

No GitHub Actions workflow was found in the inspected branch. A green status cannot be required until a branch-scoped workflow runs the selected checks and preserves logs/results.

## 6. Frozen boundaries for this sprint

1. Do not change `deterministicEngine.ts` scoring formulas, thresholds or evidence semantics unless a new falsifying test proves a defect and the owner explicitly authorizes the change.
2. Do not alter `documentNormalizer.ts` offsets or canonical hash semantics without a failing regression test.
3. Do not add fabricated provider records, canned live API results, or fake VERIFIED statuses.
4. Do not use production Supabase for writes, schema changes, migrations, or test fixtures.
5. Do not deploy, merge to `main`, or modify production secrets.
6. All persistence validation must use a disposable isolated environment or a deliberately non-persistent demo mode whose limitations are visible.
7. Distinguish STATIC, STRUCTURAL, RUNTIME and CERTIFICATION evidence. A source inspection is not a runtime PASS.
